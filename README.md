Projeto Marmita Express - MVP (Foco em Custo Zero)1. Objetivo TécnicoConstruir um protótipo funcional (MVP) de um Progressive Web App (PWA) para um restaurante de marmitas com foco em custo inicial zero. O sistema deve ser projetado para testes contínuos no GitHub e para implantação em plataformas com generosos níveis gratuitos, como Fly.io e Vercel. O core da aplicação é automatizar o fluxo de pedidos que se inicia pelo WhatsApp.2. Persona (Guia para o Desenvolvimento)Você é um desenvolvedor Full-Stack encarregado de construir este projeto do zero. Seu foco é criar um código limpo, testável e pronto para deploy, utilizando uma stack de tecnologia que minimize ou zere os custos de infraestrutura iniciais.3. Stack de Tecnologia (Opção Custo Zero)Frontend: Next.js (React) com TypeScript e Tailwind CSS. Hospedagem na Vercel (Hobby Tier - Gratuito).Backend: Node.js com Express (ou Fastify) e TypeScript. Hospedagem na Fly.io (Free Tier - Gratuito).Banco de Dados: MongoDB Atlas (Free Tier M0 - Gratuito).ORM: Mongoose.API WhatsApp (Abordagem Manual - Custo Zero): Para o MVP, o sistema não se integrará diretamente com uma API paga. Em vez disso, o painel do administrador irá:Gerar o link do cardápio do dia.Fornecer um botão "Copiar Link" para o dono do restaurante colar manualmente na conversa do WhatsApp com o cliente.Isso remove completamente a necessidade de serviços como Twilio na fase inicial.Pagamentos (Custo Transacional): Integre o SDK do Mercado Pago ou Stripe. Explicação: Não há custo fixo ou mensalidade. A cobrança é uma porcentagem sobre cada venda bem-sucedida. O custo inicial é zero.Plataforma de Deploy: Fly.io para o backend e Vercel para o frontend. Ambos possuem níveis gratuitos robustos e suficientes para o início da operação.3.1. Opção Custo-Benefício (Para Começar a Escalar)Após validar o MVP e o negócio começar a gerar receita, a primeira melhoria com bom custo-benefício é a automação do WhatsApp.API WhatsApp: Integrar com um provedor oficial como a Twilio.Justificativa: O custo é por conversa ou por mensagem, o que significa que você só paga conforme o uso aumenta. Isso profissionaliza o atendimento, economiza tempo manual e permite escalar o número de pedidos sem aumentar a equipe de atendimento proporcionalmente.4. Funcionalidades Essenciais (Backend - API)Crie os seguintes endpoints RESTful:Cardápio:GET /api/menu/today: Retorna o cardápio do dia.POST /api/admin/menu: (Protegido) Adiciona um novo prato ao cardápio geral.PUT /api/admin/menu/:id: (Protegido) Atualiza um prato.PATCH /api/admin/menu/today: (Protegido) Define quais pratos estarão ativos no dia e marca itens como "esgotados".Pedidos:POST /api/orders: Cria um novo pedido. Recebe os itens do carrinho, dados do cliente e o método de pagamento.GET /api/admin/orders: (Protegido) Lista todos os pedidos em tempo real.PATCH /api/admin/orders/:id/status: (Protegido) Atualiza o status de um pedido ("Em preparação", "Saiu para entrega").Webhooks:POST /api/webhooks/payment: Endpoint para receber a confirmação de pagamento do gateway.5. Funcionalidades Essenciais (Frontend)Crie duas interfaces distintas:Interface do Cliente (PWA):/ (Cardápio): Exibe os pratos do dia recebidos da API. Permite adicionar e remover itens./checkout (Resumo e Pagamento): Mostra o resumo do pedido, solicita nome e endereço, e apresenta as opções de pagamento (PIX e Cartão)./confirmation/:id (Confirmação): Tela final que exibe "Pedido Confirmado!" e os detalhes da compra.Interface do Admin (Painel de Controle):/admin/dashboard: Painel principal que exibe os pedidos entrando em tempo real (deve ter notificação sonora/visual). Permite a mudança de status de cada pedido./admin/menu: Interface para gerenciar o cardápio do dia, permitindo ativar/desativar pratos e marcar como esgotado. Inclui o botão para copiar o link do cardápio do dia.6. Testes e CI/CD (GitHub)Setup Local: O README.md do repositório deve ter instruções claras de como clonar, instalar dependências (npm install) e rodar o projeto localmente (npm run dev).Testes Unitários: Configure Vitest ou Jest para testes unitários da lógica de negócio no backend.GitHub Actions: Crie um workflow (.github/workflows/ci.yml) que rode o linter (ESLint) e os testes a cada push ou pull request para a branch main.7. Instruções para Deploy (Fly.io e Vercel)Containerização (Backend): Crie um Dockerfile na raiz do projeto para o serviço de backend.Configuração Fly.io (Backend): O README.md deve conter um guia sobre como usar o flyctl para fazer o deploy do backend e configurar os secrets (connection string do MongoDB Atlas, chaves de API de pagamento).Configuração Vercel (Frontend): O README.md deve explicar como conectar o repositório do GitHub à Vercel para deploys automáticos do frontend a cada push na branch main.Entregável EsperadoO resultado final deve ser um repositório no GitHub contendo:Todo o código-fonte do projeto (frontend e backend).Um Dockerfile configurado para o backend.Um README.md completo com todas as instruções de setup, teste e deploy.
